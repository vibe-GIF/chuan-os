> 日期：2026-08-24

---

## 1. 借鉴 NVIDIA AVO 的 Supervisor 定位

**核心思想**：Supervisor 不是「干活的」，是「看轨迹的 CEO」——只观察执行路径，发现问题才干预。落到 chuan-os：
- 幕僚长（初始路由）+ SupervisorMonitor（全程监控）职责分离；
- 监控旁路设计：`_monitor is None` 短路 + 全方法 try/except，监控任何异常都不阻断主流程。

## 2. 死胡同检测必须全确定性（不用 LLM）

免费模型工具调用不稳定是项目老教训，监督判断若依赖 LLM 会「不可复现、不可测试、成本高」。全部改用确定性启发式：
- **循环**：最后两次输出字符 2-gram 覆盖度 ≥0.95（小集合被大集合覆盖，容忍「同一结果 + 额外废话」）；
- **反复失败**：连续失败 ≥N 次且结果相似（≥0.7），或尝试耗尽（≥max_fail_attempts）；
- **停滞**：轨迹存活超时（watchdog）。
- **单步信号不足绝不误判**——但注意：停滞检测要独立于「≥2 步」门槛，否则单步长期悬挂永远判不出（见踩坑 3）。

## 3. 踩坑：`len(steps) < 2` 早退把停滞检测也挡掉了

初版把停滞检测放在 `len(steps) < 2` 早退之后，导致「第一步就长时间悬挂」的死胡同永远检测不到（只有一个 step，循环/反复失败需要两步信号，但停滞是时间维度，单步就该能判）。
**修正**：循环/反复失败保留 ≥2 步门槛，停滞检测移到门外独立判断。

## 4. 踩坑：测试构造「反复失败」内容时误触「循环」判定

反复失败要求相似度落在 `[0.7, 0.95)` 区间；若内容对是「完全包含」关系（如 `接口报错 500` vs `接口报错 500，重试无效`），2-gram 覆盖度 = 1.0，直接命中循环判定（≥0.95），测试断言全错。
**修正**：用部分重叠的内容对（`失败原因网络连接超时重试` vs `失败原因数据库连接超时重试`，覆盖度 ≈0.727）避开循环。

## 5. redirect 决策矩阵

| 条件 | 决策 |
|---|---|
| 循环/停滞 + 无候选 agent | abort（同 prompt 必重复，不空耗） |
| 循环/停滞 + 有候选 agent | switch_agent |
| 反复失败 + 有候选 agent | switch_agent（即使只剩最后一次） |
| 反复失败 + 无候选 + 还有次数 | inject_hint（换思路重试） |
| 反复失败 + 无候选 + 耗尽 | abort |

## 6. 接入点：重试循环的「重试前」查询

redirect 应用在 `Department._run_subtask` 的重试前（`attempt > 0` 时查死胡同）——失败发生后、重试前是最佳干预时机：abort 直接 break、switch_agent 换池内 agent、inject_hint 把提示语拼进 prompt 前缀。轨迹记录 `_record_step` 在每次尝试后统一记录，供下次判定。
