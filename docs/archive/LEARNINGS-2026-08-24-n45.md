## 1. 定位：总线/队列是「能删能重建的协调层」，真相不动

延续 N39/N43/N44「旁路增强、故障静默降级」哲学：
- **总线**（Pub/Sub）：本进程订阅者同步收到（内存分发，确定性），Redis 可用时广播跨进程；`start_listener` 拉起后台线程 `psubscribe` 收其他进程事件；
- **队列**（Streams 消费者组）：`submit`（XADD）/`pop`（XREADGROUP 认领）/`ack`（XACK+XDEL）/`requeue`（失败重试，超 `max_retries` 丢弃）/`recover`（XAUTOCLAIM 收回卡死 pending）；
- 二者绝不承担不可丢失的状态（真相仍在 SQLite / Markdown），Redis 挂了自动降级内存，不抛错不阻断。

## 2. 踩坑：redis-py 8 默认 RESP3，HELLO 握手包大，振荡网络下易超时

redis-py 8 默认走 RESP3（HELLO 命令），握手往返比 RESP2 重。Windows→WSL 跨虚拟网络本就振荡（一阵通、一阵被拒/超时），RESP3 握手常超时，表现为「TCP 能连上（socket.create_connection 通）、但 redis-py ping 超时」。
**修正**：`_connect_redis` 强制 `protocol=2`（Redis 7 完全支持），并把 `socket_connect_timeout`/`socket_timeout` 从 1s 提到 5s。改后单进程 ping 立即恢复连通。

## 3. 踩坑：redis-py 默认 `decode_responses=False` → Streams fields 键是 bytes

单测用 FakeRedis（str 键）全绿，真实 Redis 一跑 `pop` 的 payload 全是 `{}`：因为 `decode_responses=False` 时 `xreadgroup` 返回的 fields 键是 `b"task_id"`/`b"payload"`，而 `_parse` 用 str 键 `"task_id"` 查询 → 全部取不到，payload 落空。**单测没暴露是因为 FakeRedis 用了 str 键**。
**修正**：`_connect_redis` 统一 `decode_responses=True`，读写全 str，与代码内 str 键一致；同批 bus.py 一并改（listener 的 channel 处理对 str/bytes 都兼容）。改后 auto 路径 pop 拿到完整 `{'n':1,'marker':...}`。

## 4. 踩坑：Windows→WSL 跨网络振荡 → WSL 内自连绕开

Windows 侧直连 `172.30.5.62:6379` 反复 TimeoutError，好窗口极短（偶尔一次 `0 OK`）。**绕法**：直接在 WSL 内跑验证脚本连 `127.0.0.1`（本机回环稳定），用 `importlib` 直载 `chuan/bus.py` + `chuan/queue.py`（这俩只依赖 redis+yaml，不经 `chuan/__init__.py` 的 langchain 系依赖链），再传 `config.yaml` 的 host（`172.30.5.62`，WSL 自连自己也通）验证 auto 路径全链路。

## 5. 验证结论（真实 Redis，WSL 内全链路）

- 总线本地分发：`subscribe` + `publish` → 本进程 handler 同步收到；
- **跨进程**：listener 进程 `start_listener` 订阅 `agent.task` → publisher 进程 `publish` → listener 的 handler 收到 `agent.task verify.ping N45-crossproc`（经 Redis Pub/Sub 广播）✓；
- 队列 roundtrip：auto 路径 backend=redis → `submit`（pending=1）→ `pop`（task_id + 完整 payload + stream_id/retries 元数据）→ `ack`（pending=0）✓；
- 相关单测 38 passed 无回归。
